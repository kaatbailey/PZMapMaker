- **Both oracles were mutation-tested rather than trusted.** Replacing
  `javaDoubleToString` with `std::to_string` produced an immediate diff on
  `SQMETERS`/`SQFEET`. Replacing `nextInt(bound)` with the naive
  `next(31) % bound` produced 1,575 divergences out of 8,000, with the
  `nextInt(64)` rows diverging from draw zero — the power-of-two special case is
  load-bearing. A test that cannot fail proves nothing (Charter §4).
- **The `nextInt` rejection loop and power-of-two branch are the whole risk in
  the LCG.** `nextDouble`, `nextLong` and `nextBoolean` are mechanical; a naive
  `nextInt` looks correct in isolation and diverges only on some seeds.
- **Java's `\u` escape path is exercised 675 times across the real files.**
  Java appends a UTF-16 code unit; the C++ port decodes surrogate pairs and
  emits UTF-8. Verified against 日本語, 😀 (supplementary plane) and （） in the
  synthetic case.
- **Duplicate JSON keys replace in place, keeping original position**
  (`LinkedHashMap.put` semantics). Reproduced; verified with `"dup":1,"dup":2`
  → `2` at position 1.
- **`Character.isWhitespace` includes 0x1C–0x1F, which C's `isspace` does not.**
  Ported explicitly.

**Unverified** (believed, not tested — say what would test it):
- That `strtod` matches `Double.parseDouble` for every literal a feature service
  can emit. Agreed on all 15,000+ coordinates tested (compared as raw bits, not
  text) and on 1,048,293 random doubles, but the two are not specified to agree
  on hex-float or arbitrarily long decimal literals. Test: feed a generated file
  of pathological numeric literals through both.
- That the port behaves the same on malformed input. Both parsers are
  deliberately trusting and will walk off the end; neither was tested there
  because neither is specified. Test: truncated and corrupt GeoJSON, and decide
  whether matching the crash matters or whether C++ should validate.

**Corrections** (something in STATE.md / CHUNKS.md is wrong):
- **The F1 document's note that the UTF-16 vs UTF-8 collation hazard threatens
  the GIS oracles is DOWNGRADED to latent.** Measured across every real file:
  zero supplementary-plane characters, and only two characters ≥ U+E000
  (fullwidth parens U+FF08/09). The divergence needs a surrogate pair to
  trigger, so it cannot bite on this data. The digest was designed unsorted
  anyway, which removes it permanently. Recorded as measured-and-bounded rather
  than deleted.
- **For F2, Ohio is the harder dataset, not Tokyo.** Tokyo's OSM properties are
  100% strings; Ohio carries the only non-integral doubles in the corpus
  (`LONGITUDE -83.63682085642414`, `SQFEET 1371.503`, `SQMETERS 179.8132`,
  `lengthkm 1.304`). F6's "two datasets" rule holds for F2 too, for the opposite
  reason to the one stated there.

**KNOWN BOUNDED DIVERGENCE — measured, characterised, accepted:**
- `javaDoubleToString` disagrees with Java on exactly the **twenty smallest
  positive subnormal doubles**, raw bit patterns `0x1`–`0x14`, values
  4.9E-324 through 9.9E-323. Java's legacy `FloatingDecimal` emits a
  two-significant-digit form there; `std::to_chars` emits the true shortest.
  Both parse back to identical bits.
  - **Zero mismatches** over 1,048,293 random non-integral doubles spanning the
    full bit range, and 8 out of 3,000 across the subnormal sweep — all inside
    bit patterns 1–20.
  - **Unreachable from GeoJSON.** Smallest nonzero magnitude in the corpus is
    1.304. A property value would have to literally be 4.9e-324.
  - Fixing it means porting Java's `FloatingDecimal`, which is large. Recorded
    rather than fixed. **Do not rediscover this as a mystery.**

**Noticed, out of scope:**
- **The digest format needed control-character escaping.** The first version let
  a property value containing a tab or newline split across lines. Both sides
  corrupted identically so the diff still passed — it would have compared the
  wrong columns silently. OSM `description` tags do carry newlines. Fixed in
  both oracles; **`ClassifyOracle` has the same latent defect** if any tile
  `CustomName` ever contains a tab.
- `tokyo/` contains both `rivers.geojson` and `water.geojson`. STATE says OSM
  water is written as `water.geojson` because `GisImport` auto-discovers that
  name. `rivers.geojson` appears to be unread. Worth one line in E15.
- The six `*Oracle.java` harnesses are currently in the `pzgis` repo, which is
  the ODbL-exposed data repo. Fine as a temporary handoff; D3 should note it.
