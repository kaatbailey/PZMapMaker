### The port's load-bearing decision — EnumSet iteration order

Java's `masks()` takes a `Set<Dir>` and every caller passes an `EnumSet`, which
iterates in **ordinal order**. That order reaches the output in two places:
case 2, where `d[0].opposite() == d[1]` decides corner-vs-two-sides and
`corner(d[0], d[1])` takes them positionally; and case 3, where `others.get(0)`
and `others.get(1)` fix which corner is emitted first.

**This is the same class of question as `TileIndex.byName`, and it resolves the
same way** — the Java order is deterministic, so reproduce it exactly. `DirSet`
is a 4-bit mask iterated 0..3 in declaration order N, W, E, S. Not a
`std::set`, not an unordered container. M12 and M13 below confirm the decision
is load-bearing rather than defensive.

Note the declaration order is N, W, E, S — not compass order, not N, E, S, W —
and `Dir::ord` doubles as the ordinal *and* as the offset within a variant set,
so reordering the enum silently changes emitted tile indices.

### THE FINDING — the self-test is structurally blind to ordering

Seven mutations, each run against **both** instruments:

| # | mutation | digest | self-test |
|---|---|---|---|
| M8 | transpose N and W in the `Dir` table — **the original §29 bug** | DIFF 2 (`MRDIR`) | **CAUGHT** |
| M9 | `side()` draws unconditionally, ignoring `variantSets` | DIFF 1,593 — **`MRSEQ` only** | **GREEN** |
| M10 | case 4 emits corners NW,NE,**SE,SW** | DIFF 10,250 | **GREEN** |
| M11 | `corner()` swaps the E+S and S+W offsets | DIFF 51,286 | **CAUGHT** |
| M12 | case 3 builds `others` in reverse ordinal order | DIFF 41,000 | **GREEN** |
| M13 | `DirSet::toArray` iterates in reverse ordinal order | DIFF 20,500 | **GREEN** |
| M14 | `side()` uses variant base 4 instead of 12 | DIFF 28,557 | **CAUGHT** |

**Four of seven survived the self-test.** §29 warned the self-test was weak
because it never exercised the neighbour lookup; §40 measured ten mutations
surviving `BuildingPlan`'s. This measures the same thing for `MaskRule` and
identifies the *mechanism*, which neither section names:

**`check()` compares SORTED** (`MaskRule.java:241`, `sorted(got)`). That was a
deliberate fix — an earlier version compared exact sequences and failed on
correct output, and the source comment says the checker was wrong, not the rule.
The fix was right and the cost is exact: **the self-test cannot see any
ordering bug at all.** M10, M12 and M13 are all pure reorderings, all green.

That cost is not academic. Emission order reaches file bytes — `GisCells:123`
makes a tile list the lotheader's tile-index numbering. **A reordering bug is
invisible to `MaskRule`'s own test and lands in the output file.** Anything
downstream that treats a green `MaskRule` run as evidence of correct ordering is
relying on a test that structurally cannot provide it.

M9 is the second: it changes only *when* the rng is drawn, leaves every one of
