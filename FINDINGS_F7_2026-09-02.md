### The three no-diffs, adjudicated individually

**1. `dx/dy` reordered to N,W,E,S — NULL, and this is the interesting one.**
The IDENTICAL mutation in `GroundRegions` was CAUGHT at 8 lines eight hours
earlier, because `edgeDistance`'s seed loop BREAKS at the first differing
neighbour and propagates that neighbour's material into `across`. Here the
order only decides the sequence squares enter the BFS queue, and shortest-path
distances under unit edge costs are uniquely determined regardless. §40's rule —
*mutation verdicts do not transfer between steps* — demonstrated in the
direction that saves a false alarm rather than the direction that hides a bug.
This codebase now has THREE distinct direction orders (`MaskRule::Dir` N,W,E,S;
`GroundRegions::DX/DY` N,S,W,E; `TreeScatter` E,W,S,N) and only two of them are
observable.

**2. Relaxation `>` -> `>=` — NULL.** Unit edge costs plus FIFO order mean
distances are discovered non-decreasing, so a relaxation offering an equal
distance never fires. **This is the same invariant that makes the `w*h` queue
bound exactly sufficient rather than a guess** — each square is enqueued at most
once precisely because the equal case never re-enqueues. One proof, two uses.

**3. Density `>=` -> `>` — PROVABLY NULL.** `nextDouble` returns `k * 2^-53`.
None of the four band densities is such a multiple:

```
0.02  = 5764607523034235 / 2^58    -> not k*2^-53
0.035 = 1261007895663739 / 2^55    -> not k*2^-53
0.07  = 1261007895663739 / 2^54    -> not k*2^-53
0.08  = 5764607523034235 / 2^56    -> not k*2^-53
P_STUMP 0.001 = 1152921504606847 / 2^60 -> not k*2^-53
```

The tie the two operators disagree on is arithmetically unreachable. Identical
in shape to `GroundRegions`' `>= P[d]` (§ FINDINGS F5), and stronger than a
measured-unreachable claim.

**NOTE ON HONESTY.** This mutation was initially reported as caught, in a batch
summary that said "19 caught, 2 not caught". It was a miscount of the runner's
own output — three lines read NOT CAUGHT, not two. Corrected here before the
table was written, but the lesson is that a batch summary is not a measurement
either: **count from the tool's output, not from memory of it.**

### The crash, and the harness bug it exposed

`tooClose`'s `x1` clamp changed from `w-1` to `w` reads
`taken[w]` — out of range on the outer vector. The oracle **segfaults**
(`rc=-11`). Caught by the process, not by the digest — the same class as
`GroundRegions`' `P[4]` read, and further evidence that a digest cannot
adjudicate undefined behaviour.

**It surfaced a bug in the mutation runner that had been silently corrupting
results.** The digest is written only at the end of `main`, so a crashed
mutation leaves the PREVIOUS mutation's output file in place, and a runner that
does not check the exit code diffs that instead. It showed up as `tooClose`
appearing to change `bandFor` output — impossible, which is the only reason it
was noticed.

**THIS IS THE THIRD STALE-ARTEFACT FAILURE IN ONE DAY**, all the same shape:

- Ninja printing `Configuring done`, failing `manifest still dirty`, and leaving
  the old binary to run
- `javac` failing on a `TreePalette (1).java` filename, leaving stale `.class`
  files that ran and looked fine
- a crashed mutation leaving the previous mutation's digest to be diffed

**A tool that fails and leaves a usable-looking artefact behind is the standing
hazard of this project.** The general rule: delete the output first, check the
exit status, and treat a missing output as its own verdict. The runner now does.

## What is NOT covered, said plainly rather than implied

**`nextInt`'s rejection loop is unreachable from this unit.** The bound is the
palette size. Production uses 8 — a power of two, which takes
`java.util.Random`'s high-bits fast path and never enters the loop at all. For
every palette in this corpus the rejection probability `(2^31 mod bound)/2^31`
is below 1e-5, so the expected number of rejections across the entire run is
far below one.

§41's palettes corpus expected 0.02 rejections across a million draws, fired
none, and **passed on luck**. Stating the expectation is the difference between
that and this. The loop IS covered, properly, by `pz_rng_oracle` (step 2) with
adversarial bounds, and by F5's `nextInt(720000)` probe. Corpus tilesets 5 and 6
use 3 and 7 tiles so the non-power-of-two PATH is exercised even though the
rejection BRANCH inside it is not.

## `Integer.parseInt` — measured, and one known divergence

`TreePalette` reads the `tree` property through `Integer.parseInt(v.trim())`
inside a try/catch that continues on `NumberFormatException`, so exactly which
strings throw decides which tiles enter the palette. Measured 2026-09-02:

| value | Java | why it is not obvious |
|---|---|---|
| `"007"` | 7 | leading zeros are fine, it is not octal |
| `"0x2"` | throw | no hex |
| `"2\u0000"` | 2 | `trim()` strips EVERY char <= U+0020, including NUL |
| `"\u000b2"` | 2 | vertical tab likewise |
| `"1\u00a0"` | throw | NBSP is ABOVE U+0020, so trim leaves it |
| `"+2"` | 2 | `from_chars` does not accept `+`; handled explicitly |
| `"2147483648"` | throw | range |

**KNOWN DIVERGENCE, deliberate.** `parseInt` goes through `Character.digit`, so
`"\u0661\u0662"` (Arabic-Indic) parses as 12; `std::from_chars` rejects it.
Reproducing `Character.digit`'s Unicode table to service a case that cannot
occur in tile data is not worth it. **The bound is recorded with a live
falsifier**: the Java oracle throws if any corpus value contains a non-ASCII
DIGIT.

That falsifier caught its own author on the first run. It was written to ban all
non-ASCII, which fired on `"1\u00a0"` — a case worth KEEPING precisely because
it looks like it should diverge and does not. The guard was too broad; the
divergence class is narrower than "non-ASCII". Worth running once against the
vanilla tile index, when the PZ install is to hand, to confirm no real `tree`
value is non-ASCII.
