## THE HEADLINE — a UB bug in `JavaRandom`, ported in step 2, live since

**§38 records that `JavaRandom` "reproduces `java.util.Random` bit-exactly."
That is FALSE in the rejection branch of `nextInt(int)`, and has been since
step 2.** It survived steps 3, 4 and 5.

### The measurement

```fish
# 20,000 seeds, three non-power-of-two bounds
java RJ > j.txt ; ./rj > c.txt ; cmp j.txt c.txt
# *** DIVERGES *** — 6 of 20,000 seeds
```

### The mechanism

Java's loop is

```java
for (int u = r; u - (r = u % bound) + m < 0; u = next(31));
```

**The overflow IS the test.** `u - r + m` is only negative when the addition
wraps, and Java defines that as two's-complement wraparound. The C++ was a
faithful transcription of the source — and therefore undefined behaviour, since
signed overflow is UB in C++. At `-O2`, GCC proves `u - r + m >= 0` from
`u >= r >= 0` and `m >= 0`, **deletes the branch, and the loop never rejects.**

| build | vs `java.util.Random` |
|---|---|
| `-O0` | IDENTICAL |
| `-O2` | **DIVERGES** |
| `-O2 -fwrapv` | IDENTICAL |

That table is the proof it is UB and not arithmetic: the same source, the same
compiler, different optimisation, different answer.

### The fix, and why not `-fwrapv`

The arithmetic now runs in `uint32_t`, where wraparound is defined, and converts
back — well defined under C++20's two's-complement model. `-fwrapv` would also
work and was rejected: it hides the hazard behind a build flag that a later
`CMakeLists.txt` edit could drop silently, restoring the bug with no source
change to blame.

Verified after the fix:

- identical at `-O0`, `-O1`, `-O2`, `-O3`, `-Ofast`
- identical over **2,000,000 draws**, 200,000 seeds × 10 bounds, including
  `1073741825` (a power of two plus one) and `1000000007`

### WHY THREE PORT STEPS MISSED IT — and this is the part worth keeping

Rejection probability for a bound is `(2^31 mod bound) / 2^31`.

| bound | rejection probability | used by |
|---|---|---|
| `nextInt(100)` | 48/2³¹ ≈ **2.2e-8** | the palettes corpus |
| `nextInt(4)`, `nextInt(2)` | 0 — power of two, different branch | palettes |
| `nextInt(720000)` | 443,648/2³¹ ≈ **2.1e-4** | this step's corpus |

Across roughly a million `nextInt(100)` draws the palettes chunk expected
**0.02** rejections. It never fired. **The palettes chunk passed on luck, not
on correctness** — confirmed directly: after the fix the palettes digest is
**unchanged at `d28516268cdaae203275e778b2176563`**, proving both that the fix
broke nothing and that that corpus never reached the branch.

**The lesson: choose corpus bounds adversarially, not conveniently.** A bound of
100 looks like a reasonable choice and is nearly the worst possible probe for
this branch. The bug was found because step 6 happened to need 720000.

**This also means §40's advice generalises further than it was written.** §40
said prove a no-diff mutation unreachable before blaming the oracle. The mirror
case is here: a *passing* oracle can be passing because the corpus cannot reach
the defect, and byte-identical agreement over millions of draws said nothing
about a branch entered 0.02 times.

step 5. Steps 3 and 4 have not been re-run and should be, since it costs one

## The transcendental — characterised, and it is NOT `std::cos`'s fault

`GisImport.java:124` is the only transcendental in step 6:

```java
double mPerLon = 111_320.0 * Math.cos(Math.toRadians(midLat));
```

Called **once per import**, but its result feeds `Math.ceil` for the grid width,
so one ulp does not nudge a coordinate — it can resize the grid and diverge
every cell at once.

Measured over a 257,143-sample sweep of −90..+90:

| version | divergent samples |
|---|---|
| naive transcription | **40,898 (15.9%)** |
| after correcting `toRadians` | **531 (0.21%)** |

**The 15.9% was a transcription bug, not a `cos` disagreement.**
**`Math.toRadians(a)` is NOT `a / 180.0 * PI`** — modern OpenJDK is a single
multiply by `DEGREES_TO_RADIANS = 0.017453292519943295`. The two differ by one
ulp on some inputs, and near ±90° `cos ≈ 0` amplifies that ~32,768×, which is
exactly the bit-delta observed. Had `toRadians` and `cos` not been separated,
the obvious conclusion would have been "`std::cos` is unusable, port fdlibm."

**Do not port fdlibm.** At 41.5°, `Math.cos` and `StrictMath.cos` disagree while
`std::cos` matches `Math.cos`. Chasing `StrictMath` would make agreement
**worse**.

The residual 531 are genuine `Math.cos` vs `std::cos` one-ulp disagreements at
ordinary latitudes — **258 within |lat| ≤ 60**, e.g. −59.6886, −58.7359. Not a
polar artifact.

**Decision: characterise and accept, do not eliminate.** The corpus seeds 18 of
those known-divergent latitudes deliberately, so the oracle answers the question
that matters rather than avoiding it.

## THE REAL UB HAZARD IS `hash01`, AND NOTHING HAD FLAGGED IT

`GroundRegions.hash01` (`:291-299`) is a SplitMix64 finaliser computed in Java
`long`. All four constants exceed 2^63, so they are negative Java longs; every
multiply overflows; `>>>` is a logical shift. **This is structurally the same
bug this document found in `nextInt` one step earlier**, and it sits in the
function that decides every dither flip in the generated map.

The port runs entirely in `std::uint64_t`. That decision is measured, not
argued:

| form | digest | UBSan |
|---|---|---|
| shipped, `uint64_t` throughout | identical, all five `-O` levels | **0 reports** |
| full `int64_t` transcription | **11,401 divergent lines** | signed overflow |
| multiplies only in `int64_t`, shifts left logical | **NOT CAUGHT at -O2** | **8 signed-overflow reports** |

The third row is the one worth keeping. The naive multiply is undefined
behaviour that GCC 13 at `-O2` happens not to exploit, so the digest clears and
the code looks fine. UBSan names it:

```
groundregions.cpp:217: runtime error: signed integer overflow:
    -4417276706297103279 * -49064778989728563 cannot be represented in 'long int'
```

**This is the F5 headline with the sign reversed.** There, UB manifested and a
passing corpus hid it. Here the corpus is strong enough to catch the *full*
naive transcription (11,401 lines, because the arithmetic shift diverges even
where the overflow does not) while the *partial* one slips through. A digest
cannot adjudicate undefined behaviour; a sanitizer can. **Run UBSan on any
Track F unit that transcribes Java integer arithmetic.**

The shipped port under `-fsanitize=undefined,address` produces zero reports and
is still byte-identical to Java.

| line | outcome | why it cannot be taken |
|---|---|---|
| `dither`: `other == nullptr` | never | `edgeDistance` sets `d` and `across` together, and `d < 0` was already skipped |

**The induction.** `edgeDistance` propagates into a square only when that

material X, so its material is X; it inherits that square's `across` = Y, and
Y != X held at the seed. So `across != material` at every distance. Both guards
are dead given the function's own contract.

**gcov is the right instrument here and instrumentation is the wrong one.**
Adding counters to the unit would have landed in both trees and become part of
the digest; gcov measures the shipped source and changes nothing.

### The five no-diffs, adjudicated individually

§41 established that lumping no-diffs together gives the wrong answer. It did
again: these five are four different things.

**1. `>= P[d]` -> `> P[d]` — PROVABLY NULL, and provable is stronger than
measured.** `hash01` returns `k * 2^-53` for integer k. None of the four `P`
values is such a multiple — `0.06` is exactly `1080863910568919 / 2^54`, and
`0.03`, `0.01`, `0.005` likewise sit at finer exponents. Equality is
arithmetically impossible, so the two operators are the same function here.
This is a stronger claim than §41's M16, which was only *measured* unreachable
at 0 ties in 1.4M comparisons.

**2 and 3. The snapshot in `dither` is DEAD CODE.** Replacing `src` with `mat`
in the null guard leaves the digest untouched; so does removing the snapshot
copy outright. `dither` writes only the square it is currently visiting and
reads only that same square, and each square is visited once, so no read ever
observes an updated neighbour. The Java comment says the snapshot exists so
"a flipped square cannot seed further flips" — nothing could. **Ported
faithfully anyway**: deleting code during a port weakens the oracle for no gain
(§40's fourteen dead symbols, same reasoning). Cleanup belongs in a later chunk
applied to both trees at once.

**4. `hash01` multiplies in `int64_t` — UB, not null.** See the table above. Not
caught by the digest; caught immediately by UBSan.

**5. `d >= P.size()` -> `>` — INVISIBLE TO ANY DIGEST.** It reads `P[4]`, one
past a `std::array<double,4>`:

```
groundregions.cpp:123: runtime error: load of address 0x... with
    insufficient space for an object of type 'const double'
```

The corpus *does* reach `d == 4` — this is not a coverage gap. The digest
simply cannot model an out-of-bounds read whose value happens to make the
comparison false. Same class as the raster oracle's `deriveWalls` case below.
**The instrument is a sanitizer, not a stronger corpus.**

### The drop note's build instructions were wrong, in an ordering that mattered

`DROP_step6_2_2026-09-02.md` said to `touch *.cpp *.hpp CMakeLists.txt` under a
"Before building" heading, ahead of the copy step. Two defects, and the first
run hit both:

1. **`touch` before `cp` does nothing for the copied files.** A file copied in
   afterwards arrives carrying its future mtime intact, so Ninja loops
   `manifest 'build.ninja' still dirty after 100 tries` exactly as before. The
   copy has to come first.
2. **The extension glob misses files.** `*.cpp *.hpp CMakeLists.txt` does not
   match `GroundRegionsOracle.java`, and the Java tree's copy of it is a
   different file in a different repo that the glob cannot reach at all.

STATE §36 already warns to `touch` including `CMakeLists.txt` by name. What it
does not say, and what cost this drop a round trip, is that **an extension list
is the wrong instrument.** The catch-all is:

```fish
find ~/Documents/PZMapMaker ~/Documents/PZMapCreation -not -path '*/.git/*' \
     -type f -newermt now -exec touch {} +

# Must print nothing:
find ~/Documents/PZMapMaker ~/Documents/PZMapCreation -not -path '*/.git/*' \
     -type f -newermt now
```

Run it **after** every file is in place, across **both** repos, and delete the
build directory rather than reconfiguring into it — `/tmp/noqt`'s `build.ninja`
has already recorded the future stamps and will keep looping after the sources
are fixed.

`VERIFY.md`'s "Environment, before running anything" block carries the corrected
form.

### A second, independent failure in the same run

`javac` reported `file not found: src/main/java/pzformat/GroundRegionsOracle.java`
and `java` then failed with `ClassNotFoundException`. That was not the mtime
problem: the Java oracle had not been copied from the C++ repo root into
`PZMapCreation/src/main/java/pzformat/`.

**That copy is the step most likely to be skipped, because it is the one that
leaves a repo.** It is the same shape as the `GeoJsonOracle.java` incident
(§38), where an oracle landed empty and a later session could have assumed it
was never written. The guard is cheap and belongs in every future drop:

```fish
wc -l ~/Documents/PZMapMaker/GroundRegionsOracle.java \
      ~/Documents/PZMapCreation/src/main/java/pzformat/GroundRegionsOracle.java
# both must read 568
```
