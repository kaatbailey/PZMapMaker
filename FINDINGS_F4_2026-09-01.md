### The port's load-bearing decision — EnumSet iteration order

Java's `masks()` takes a `Set<Dir>` and every caller passes an `EnumSet`, which
iterates in **ordinal order**. That order reaches the output in two places:
case 2, where `d[0].opposite() == d[1]` decides corner-vs-two-sides and
`corner(d[0], d[1])` takes them positionally; and case 3, where `others.get(0)`
and `others.get(1)` fix which corner is emitted first.

**This is the same class of question as `TileIndex.byName`, and it resolves the
same way** — the Java order is deterministic, so reproduce it exactly. `DirSet`
is a 4-bit mask iterated 0..3 in declaration order N, W, E, S. Not a
`std::set`, not an unordered container. M12 and M13 below confirm the decision
is load-bearing rather than defensive.

Note the declaration order is N, W, E, S — not compass order, not N, E, S, W —
and `Dir::ord` doubles as the ordinal *and* as the offset within a variant set,
so reordering the enum silently changes emitted tile indices.

## K. Unit 3 of 4 — `GroundPalette` — PORTED. The oracle needed strengthening TWICE.

206 Java lines → `groundpalette.hpp` (133) + `groundpalette.cpp` (141). First

**Final digest: 345,732 lines, 14,978,074 bytes, md5
`f4ed4cb4acbc7440280bc8e19b0f49bd`.** Expiring; `022d938` / `7cda6c2`, g++

The two `stdout` side-effect line counts also match at 87 — `pick()` prints when

### Floating point — why this ported cleanly where §39 did not

Cumulative weight tables, `nextDouble() * total`, two threshold comparisons.
Java has been strict-FP since 17, and **every operation here is a bare add,
multiply or compare — there is no `a*b+c` anywhere**, so there is no
FMA-contraction opportunity. §39's `minAreaRect` divergence was transcendentals;
there are none in this unit. The chunk prompt said not to go looking for §39's
problem here, and that is correct — but the reason is worth writing down, because
it is a property of the arithmetic and not a general fact about the file.

`GPROWW` digests `rowWeightOf` as raw IEEE-754 bits rather than as printed
decimals, so a one-ulp difference cannot hide behind `%f`.

### THE FIRST STRENGTHENING — a byte-identical digest over a corpus that tested almost nothing

The first corpus drew a flat 4-way choice per candidate tile: absent /
tiledefs-only / sprites-only / both. It produced a **byte-identical** digest.
It was nearly worthless:

| | first corpus | after modes |
|---|---|---|
| cases where `pick()` throws | **4,914 / 5,000** | 1,843 |
| cases keeping 3 groups | **0** | 2,114 |
| cases keeping 2 groups | 1 | 479 |
| cases keeping 1 group | 85 | 564 |
| cases with **0 tufts** — the short-circuit path | **0** | 983 |

A group survives only if all four of its base tiles land in both sets, p =
(1/4)⁴ = 1/256, so the corpus collapsed onto one throw. **Zero cases reached the
empty-tuft branch — the branch that changes `roll()`'s DRAW COUNT**, because
Java short-circuits `!tufts.isEmpty() && rng.nextDouble() < rate`.

Fixed by replacing uniform randomness with eight explicit modes (all-present;
bases-but-no-tufts; one variant missing; thinned; no bases at all; and three
mixed rates), drawing two rng values per candidate **in every mode** so the
stream stays aligned and a mode change can never be mistaken for a draw-count
change.

**This is §40's lesson recurring, and it is worth stating in its general form:
byte-identical agreement is evidence about the code only to the extent the
corpus reaches it. The first digest agreed on 5,000 cases and exercised four
branches.**

### THE SECOND STRENGTHENING — a no-diff mutation that was the ORACLE's fault, not the code's

Seven mutations. Five diffed immediately:

| # | mutation | result |
|---|---|---|
| M15 | `roll()` tests `tuftRate` before the `isEmpty` guard | DIFF 15,823 — `GPROLL` only |
| M16 | group walk `r > cum` → `r >= cum` | **NO DIFF** — see below |
| M17 | swap the dense/medium group weights | DIFF 54,084 |
| M18 | tuft row weight 6.20 → 6.02 | DIFF 2,197 |
| M19 | `all[]` emits tufts before bases | DIFF 2,174 — `GPALL` only |
| M20 | `pick()` stops listing after the first missing variant | **NO DIFF** → then DIFF 1,769 |
| M21 | `TUFT_USABLE_COLS` 6 → 8 | DIFF 23,793 |

**M20 was not a null mutation — it was a hole.** `dropped` has exactly two
observables: the count in `pick()`'s stdout line, and the list embedded in the
exception message. The digest read **neither**, recording only that a case
threw. So a mutation that changes which tiles get reported passed clean.

§40's rule says prove a no-diff mutation unreachable before calling the oracle
weak. Applying it honestly here gives the opposite verdict from §I's M7: the
mutation **is** reachable, it changes real output, and the instrument was not
looking. Fixed by digesting `e.getMessage()` / `e.what()` rather than the bare
fact of the throw. Re-run: **DIFF 1,769 `GPTHROW` lines.**

**M19 deserves note too.** It diverges in `GPALL` and nowhere else — and `all`
is the list a cell header declares, so its order **is** the file's tile-index

reordering there is invisible and lands in the output file. Same shape as §J's
finding about `MaskRule`'s sorted comparison.

### M16 — measured unreachable, and that claim is deliberately weak

`r > cum[gi]` and `r >= cum[gi]` differ only when `r` exactly equals a
cumulative bound. Instrumented over the four cumulative tables the corpus can
produce, 200,000 seeds:

```

```

**This is evidence, not proof.** `nextDouble()` yields k/2⁵³ and nothing rules
out an exact hit a priori; 0 in 1.4M says it does not happen at this scale, not
that it cannot. Recorded as **measured unreachable at 1.4M comparisons**,
stamped, and re-checkable by re-running the instrument. Unlike §I's M7 — where
distinctness of 14 keys makes scan direction provably irrelevant — this one does
not get to be called null.

## L. STANDING RULE — every file crossing from a session container into the owner's tree arrives ~4 HOURS IN THE FUTURE

**Measured 2026-09-01, and it had already been reported verbally in an earlier
session and never written down. That omission cost roughly six turns in this
one.** It is recorded here so no session rediscovers it again.

```fish
date
stat -c '%y %n' ~/Documents/PZMapMaker/CMakeLists.txt
# Tue Sep  1 08:51:24 PM EDT 2026
# 2026-09-02 00:43:56.000000000 -0400  .../CMakeLists.txt
```

**The mechanism.** Session containers write mtimes in UTC. The owner's machine
is EDT, UTC−4. A file authored off-machine therefore lands stamped up to four
hours ahead of the local clock.

**The symptom, and why it is hard to read.** Ninja fails with:

```
ninja: error: manifest 'build.ninja' still dirty after 100 tries,
perhaps system time is not set
```

CMake reports `Configuring done` / `Generating done` first, so **the failure
looks like a successful configure**. Ninja then builds nothing, the previous
executable is left in place, and the oracle runs the OLD BINARY. That is the
worst possible shape: a green-looking build producing a stale, self-consistent
result. Here it surfaced as the Java side emitting 345,732 lines while the C++
side emitted 254,354 — the two-unit digest from the drop before.

`rm -rf` on the build directory does NOT fix it. The future mtime is on the
source file, not the build tree, so a fresh configure reproduces it exactly.

**THE RULE. Every file copied from a session into either repo must be `touch`ed
before any build.** The chunk prompt already carried "`touch` files authored
off-machine, or Ninja loops 'manifest still dirty'" — that instruction is
correct and its *reason* is this. What the prompt does not say, and what cost
the turns:

- **`CMakeLists.txt` is the file most likely to be missed**, because the usual
  incantation is `touch *.cpp *.hpp` and CMakeLists matches neither. It is also
  the file whose staleness is most damaging, since it gates whether new sources
  are compiled at all. Measured here: every `.cpp`/`.hpp` had been touched and
  `CMakeLists.txt` alone was still four hours ahead.
- Touch **everything dropped**, not just the sources:

```fish
touch ~/Documents/PZMapMaker/*.cpp ~/Documents/PZMapMaker/*.hpp \
      ~/Documents/PZMapMaker/CMakeLists.txt \
      ~/Documents/PZMapCreation/src/main/java/pzformat/*.java
```

- To catch it generally rather than by listing extensions:

```fish
find ~/Documents/PZMapMaker ~/Documents/PZMapCreation -newermt now -exec touch {} \;
```

**Verification is by content, never by mtime.** `find -newermt '-1 hour'` was
used twice in this session to ask "did the new file arrive?" and answered
falsely both times — once because a blanket `touch` had rewritten the mtime of
an old file, once because the search excluded the directory the files were
actually in. `wc -l` on the file answered correctly every time. A file's
timestamp says nothing about its contents, and in this tree it does not even
reliably say when it arrived.

**Delivery rule that follows from this.** A session hands over COMPLETE FILES,
never edits to apply, and every drop is accompanied by the expected `wc -l` of
each file so the owner can confirm the right version landed before building.
Line counts distinguish drop N from drop N+1; mtimes do not.

### The collation caveat — real, and localised exactly

`tilepalette.hpp` PORT NOTE 3 warns that Java sorts by UTF-16 code unit and C++
by UTF-8 byte. Tested rather than asserted, comparing sort ORDER by ASCII label
so console re-encoding cannot confound it:

```
Java (UTF-16 code unit): ascii_a U+10000 U+FFFD
C++  (UTF-8 byte)      : ascii_a U+FFFD  U+10000
*** ORDER DIVERGES ***
```

**The boundary is exact.** UTF-8 byte order preserves code-point order by
design, so Latin-1 and BMP names agree — a first test with `é`, `ÿ`, `Ā` showed
no divergence at all. Java compares UTF-16 **code units**, which departs from
code-point order only for supplementary characters: U+10000 encodes as the
surrogate pair `D800 DC00`, and `0xD800 < 0xFFFD`, so Java sorts U+10000 before
U+FFFD while C++ sorts it after.

**Reachability: requires a tile name containing a character at or above U+10000
alongside one in U+E000..U+FFFF.** Every vanilla tile name is ASCII, so this is
unreachable on shipped data — but unreachable by DATA, not by construction. A
mod shipping an emoji in a tile name would diverge. **Recorded, not fixed**;
fixing it means implementing UTF-16 code-unit comparison in C++, which is real
work for a case that does not occur, and the decision should be deliberate
rather than a side effect of this chunk.
